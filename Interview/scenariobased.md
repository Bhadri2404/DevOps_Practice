## 1. High‑Level Production Scenario

**One‑liner you can say in interviews**

> “In our hybrid environment (on‑prem + AWS), secrets are managed centrally and injected into the lifecycle at three layers:  
>  1) Terraform/Ansible for infra and configuration,  
>  2) CI (Jenkins/GitHub Actions) for deployment,  
>  3) Kubernetes/Argo CD for runtime, using Kubernetes Secrets and external secret stores.”[web:226][web:228][web:235]

---

## 2. Kubernetes Secrets in Production

### 2.1 How you used Kubernetes Secrets

**Scenario**: Microservices on EKS/AKS/on‑prem K8s needing DB creds & API keys.

1. Each application had **environment‑specific Secrets**, for example:
   - `orders-api-db-secret-dev`, `orders-api-db-secret-prod`.  
2. Secrets contained:
   - DB username/password,  
   - Third‑party API keys (payment gateway, logging SaaS),  
   - Internal service tokens (e.g., IBM/ELM API tokens).[web:229][web:235]  
3. Secrets were **not stored in plain YAML** in Git; they were:
   - Either generated by CI using values from a vault (AWS Secrets Manager / Ansible Vault), then applied with `kubectl`, or  
   - Pulled dynamically at runtime using an External Secrets / Argo CD secrets integration.[web:228][web:238]  

### 2.2 Example and explanation

Secret (Git repo only stores the *template* or reference):

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: orders-api-db-secret
  namespace: prod
type: Opaque
data:
  username: {{ BASE64_ENCODED_DB_USER }}
  password: {{ BASE64_ENCODED_DB_PASS }}
```

- `kind: Secret`: Marks this as a Kubernetes Secret object.[web:229]  
- `namespace: prod`: Secret is isolated to the production namespace (dev has a different one).  
- `data.username/password`: Base64‑encoded values; raw passwords are never committed to Git. They are templated and filled via CI or Argo CD secret plugin.[web:226][web:235]  

Deployment:

```yaml
env:
  - name: DB_USER
    valueFrom:
      secretKeyRef:
        name: orders-api-db-secret
        key: username
  - name: DB_PASS
    valueFrom:
      secretKeyRef:
        name: orders-api-db-secret
        key: password
```

- `valueFrom.secretKeyRef`: Injects secrets as environment variables without hardcoding them in the image.  
- Only this microservice’s Pod reads `orders-api-db-secret`, enforced via namespace + RBAC.[web:226][web:228]  

**Interview line**

> “We used Kubernetes Secrets per app and per environment, and injected them via env vars or volume mounts. Secrets themselves were synced from central stores (Ansible Vault / AWS Secrets Manager) either through CI or Argo CD integrations, so no clear‑text secrets lived in Git.”

## 3. Ansible Vault for Configuration and Deployments

### 3.1 Where Ansible Vault fits

From your resume, you used **Ansible Tower** to automate on‑prem Linux servers, Jenkins nodes, and some infra tasks.[file:241]  

**Scenario**: Managing OS‑level and middleware secrets (system accounts, DB root, SSL keys).

1. Sensitive variables were stored in:
   - `group_vars/prod/vault.yml` (encrypted),  
   - `host_vars/jenkins-master/vault.yml` etc.  
2. Encryption was done with:
   - `ansible-vault encrypt group_vars/prod/vault.yml`.  
3. Vault passwords were:
   - Stored securely in Ansible Tower credentials, **not** in Git,  
   - Or injected via Jenkins credentials when running `ansible-playbook` from pipelines.[web:232][web:237]  

### 3.2 Example and explanation

Encrypted group vars (conceptual):

```yaml
# group_vars/prod/vault.yml (stored encrypted)
db_root_password: "S3cr3t#Prod!"
jenkins_admin_password: "Adm1n#Pass!"
tls_key: |
  -----BEGIN PRIVATE KEY-----
  ...
  -----END PRIVATE KEY-----
```

- File is fully encrypted at rest using Ansible Vault; Git only sees ciphertext.[web:232]  
- `db_root_password`: Used in MySQL/Postgres setup roles.  
- `jenkins_admin_password`: Used when bootstrapping Jenkins master.  
- `tls_key`: Injected into `/etc/nginx/ssl/app.key` on target nodes.  

**How it runs from CI**

```bash
ansible-playbook site.yml \
  -i inventories/prod/hosts \
  --vault-password-file /run/secrets/vault_pass
```

- `--vault-password-file`: Provided by Jenkins or Tower from a credential store, not committed.  
- CI job has permission to run this, so secrets are decrypted *just‑in‑time* on the controller and pushed to target hosts.

**Interview line**

> “We used Ansible Vault to encrypt OS‑level and middleware secrets (root passwords, TLS keys) and integrated it with Ansible Tower and Jenkins. Vault passwords were stored in credential stores, so playbooks could run non‑interactively in CI while keeping secrets encrypted in Git.”

## 4. Terraform, Jenkins, and Secret Integration

### 4.1 Terraform + Jenkins

From your resume, you contributed to Terraform IaC and ran it through Jenkins/GitHub Actions.[file:241]  

**Scenario**: Provision AWS VPC, EKS, RDS, and IAM using Terraform, with Jenkins as orchestrator.

1. Terraform code is in Git (no secrets hardcoded).  
2. Sensitive values (DB passwords, API keys) are passed via:
   - Terraform variables (`var.db_password`),  
   - Encrypted Jenkins credentials mapped to environment variables (`TF_VAR_db_password`).[web:234][web:239]  
3. Terraform stores outputs:
   - Non‑sensitive values (cluster endpoint, role ARNs) in state and outputs,  
   - Sensitive values either **not** output, or only marked as `sensitive = true` so they are redacted in CLI.[web:236]  

Simple `variables.tf`:

```hcl
variable "db_password" {
  type      = string
  sensitive = true
}
```

Jenkins pipeline snippet:

```groovy
environment {
  TF_VAR_db_password = credentials('prod-db-password') // Jenkins credential ID
}
steps {
  sh 'terraform init'
  sh 'terraform apply -auto-approve'
}
```

- Jenkins pulls the actual secret from its credential store and exposes it as `TF_VAR_db_password`.  
- Terraform reads it as `var.db_password` without committing it anywhere in Git.[web:234]  

**Interview line**

> “Terraform code was fully in Git, but secrets like DB passwords were injected at runtime from Jenkins credentials as `TF_VAR_` environment variables, marked as sensitive in Terraform so they never appeared in logs or plans.”

## 5. Jenkins → Argo CD → Kubernetes (GitOps with Secrets)

### 5.1 How Argo CD replaces direct Jenkins deploys

From your work: you’re moving from “Jenkins directly deploys to K8s” to “Jenkins triggers Argo CD, and Argo CD syncs from Git”.[file:241][web:239]  

**Scenario**: Hybrid GitOps deployment of microservices to EKS/AKS.

1. **App manifests/Helm charts** live in a Git repo:
   - Deployments, Services, Ingress, and **references to Secrets** (names only).  
2. **Argo CD** watches that repo and syncs to the cluster:
   - Jenkins does not `kubectl apply` directly; it bumps image tags in Git or triggers sync.  
3. Secrets are managed via:
   - Argo CD + secret plugins (e.g., SOPS, Vault, or External Secrets), or  
   - Pre‑created Kubernetes Secrets (via Terraform/Ansible/CI) that Argo CD simply consumes.[web:236][web:238]  

### 5.2 Example Argo CD flow

1. Jenkins pipeline builds and pushes image:
   - `orders-api:1.2.3` to ECR/ACR.  
2. Jenkins updates Git **values file**:
   - `values-prod.yaml` – `image.tag: "1.2.3"`.  
3. Jenkins commits and pushes; optionally calls Argo CD API to sync:
   - `argocd app sync orders-api-prod`.  
4. Argo CD deploys:
   - Uses Helm/Kustomize to create Deployment referencing `orders-api-db-secret`.  
5. Secrets:
   - Already exist in the cluster (created previously by Terraform/Ansible or managed by Argo CD Vault plugin).[web:238][web:239]  

**Interview line**

> “We moved to GitOps using Argo CD, where manifests and Helm values live in Git. Jenkins’ role is to build images, update tags in Git, and optionally trigger Argo CD sync. Secrets are managed separately via Kubernetes Secrets and secret‑management integrations, so no plaintext secrets appear in the GitOps repo.”

---

## 6. End‑to‑End Narrative (Hybrid Architecture)

This is a story you can give as a complete answer.

1. **Provisioning (Terraform)**  
   - Terraform provisions AWS VPC, EKS cluster, RDS, IAM roles, and sometimes on‑prem connectivity (VPN/Direct Connect).  
   - Sensitive inputs (DB passwords, API tokens) come from Jenkins/GitHub Actions credentials via `TF_VAR_` variables and are marked `sensitive` in Terraform.  

2. **Configuration (Ansible Tower)**  
   - Ansible Tower configures on‑prem Linux servers, Jenkins nodes, and some app servers.  
   - Secrets (root passwords, TLS keys, service accounts) are stored in Ansible Vault encrypted files; Tower/Jenkins injects the vault password at runtime.  

3. **Runtime (Kubernetes + Argo CD)**  
   - Applications run on Kubernetes (EKS/AKS/on‑prem).  
   - Each application uses Kubernetes Secrets per environment; secrets are synced from vaults or provisioned via CI/Terraform/Ansible.  
   - Argo CD handles deployments (GitOps). Jenkins only pushes images and updates Git; Argo CD syncs to clusters.  

4. **Security & Governance**  
   - No plain‑text secrets in Git; only encrypted Vault files or secret names.  
   - Secret access is restricted by namespace, ServiceAccount, and IAM (for cloud secret managers).  
   - Rotations are handled centrally (update in vault, sync to K8s; update Terraform/Ansible variables via CI).

## 9. Email Alerting When Server / Application Is Down

### 9.1 High‑level story

> “We used metrics + alerting (Prometheus / CloudWatch) to detect when servers or applications were down, and then routed alerts through Alertmanager or SNS to send email notifications to the on‑call DevOps/Ops team. Grafana was used to visualize and sometimes send additional alerts.”[file:241][web:257][web:259][web:262]

---

### 9.2 Kubernetes / Linux servers – Prometheus + Alertmanager + email

**Scenario**: “Alert when a Kubernetes service or Linux node is down.”

#### Step 1 – Prometheus scrapes targets

1. Prometheus is configured to scrape:
   - Kubernetes nodes and Pods via service discovery.  
   - Linux node exporters for CPU/RAM/disk.  
2. For each target, Prometheus keeps a time‑series metric like:
   - `up{job="kubernetes-nodes", instance="node1"}`  
   - `up{job="node-exporter", instance="onprem-server1"}`[web:265]  

If `up` goes from `1` to `0`, Prometheus knows the target is **down or unreachable**.[web:265]

#### Step 2 – Alert rule for “down” target

Example alert rule:

```yaml
groups:
  - name: availability.rules
    rules:
      - alert: InstanceDown
        expr: up == 0
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "Instance {{ $labels.instance }} is down"
          description: "More than 5 minutes without a successful scrape."
```

- `expr: up == 0`: Trigger when any monitored instance stops responding.  
- `for: 5m`: Avoid flapping; only alert if it stays down for 5 minutes.  
- `severity: critical`: Used for routing rules (critical → email, pager, etc.).[web:265]  

#### Step 3 – Alertmanager routes to email

Alertmanager config (simplified):

```yaml
route:
  receiver: 'email'
  group_by: ['alertname']
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 1h

receivers:
  - name: 'email'
    email_configs:
      - to: 'devops-oncall@company.com'
        from: 'alerts@company.com'
        smarthost: 'smtp.company.com:587'
        auth_username: 'alerts@company.com'
        auth_password: 'SMTP_APP_PASSWORD'
```

- `route.receiver: 'email'`: All alerts go to the `email` receiver by default.[web:261][web:265]  
- `group_by`: Group similar alerts so you don’t get spammed.  
- `email_configs`: Tells Alertmanager how to send email via SMTP (sender, recipient, mail server, auth).[web:261]  

**What happens when a node or app is down**

1. Prometheus sees `up == 0` for more than 5 minutes.  
2. It fires `InstanceDown`.  
3. Alertmanager receives the alert and routes it to the `email` receiver.  
4. Email is sent to `devops-oncall@company.com` with a subject like “Instance node1 is down”.[web:257][web:261]  

**Interview line**

> “We used Prometheus alert rules like `up == 0` with a 5‑minute `for` period to detect node and service outages. Alertmanager routed `severity=critical` alerts to our on‑call email group using SMTP, so whenever a server or critical microservice went down we were notified immediately.”

### 9.3 Application‑level alerts – Grafana email alerts (optional)

**Scenario**: “Alert when HTTP error rate or response time is bad.”

1. Prometheus stores metrics like `http_requests_total` and `http_request_duration_seconds`.  
2. Grafana dashboards visualize these metrics.  
3. Grafana alert rules are attached to panels:
   - Example: “If error rate > 5% for 5 minutes, send email alert.”[web:259][web:263]  

Email integration in Grafana:

- Configure SMTP in `grafana.ini` (`[smtp]` section).  
- Create an **email contact point** in Grafana with the DevOps on‑call address.[web:259]  
- Attach this contact point to alert rules.

**Interview line**

> “For application‑level SLOs (error rate, latency), we used Grafana alerting on top of Prometheus metrics with email contact points, so the team received clear ‘service X 5xx rate > 5%’ alerts.”

### 9.4 AWS servers – CloudWatch Alarm + SNS + email

**Scenario**: “Alert when an EC2 instance or application on EC2 is down.”

#### Step 1 – CloudWatch metric

1. For EC2:
   - `StatusCheckFailed` or `StatusCheckFailed_System` metrics indicate instance problems.  
2. For an HTTP app:
   - A CloudWatch Synthetic or a custom metric (e.g., success of a health‑check Lambda) is used.[web:262][web:266]  

#### Step 2 – SNS topic with email subscription

1. Create an SNS topic, e.g., `server-down-alerts`.  
2. Subscribe your on‑call email: `devops-oncall@company.com` as an email endpoint.[web:262][web:266]  

#### Step 3 – CloudWatch Alarm

Example: alarm on `StatusCheckFailed` > 0 for 5 minutes.

- In CloudWatch, create an alarm:
  - Metric: `StatusCheckFailed` for the instance.  
  - Condition: `> 0` for 2 out of 2 data points.  
  - Action: “Send notification to SNS topic `server-down-alerts`”.[web:262][web:266]  

**What happens**

1. EC2 fails status checks / app health check fails.  
2. CloudWatch Alarm enters `ALARM` state.  
3. Alarm publishes a message to SNS topic.  
4. SNS sends email to all subscribed addresses.[web:262][web:266]  

**Interview line**

> “For AWS resources we used CloudWatch Alarms on instance and application metrics, wired to SNS topics with email subscriptions. Whenever an EC2 or app health check failed, CloudWatch → SNS → email alerted the on‑call DevOps group.”

## 10. Full Hybrid Flow – From Code to Prod with Secrets, Artifacts, and Alerts

### 10.1 Scenario: New release of “orders‑api” to EKS (AWS) and on‑prem test cluster

Interview question you might get:

> “Walk me through, end‑to‑end, what happens when you release a new version of your orders service, including how secrets, artifacts, and alerts are handled in your hybrid environment?”

#### Step 1 – Developer changes code

1. Developer pushes to `feature/*` branch → opens PR.  
2. Jenkins / GitHub Actions runs:
   - Unit tests, linting.  
   - Optional security scans (SAST/Trivy on Docker image).  

Secrets at this stage:

- SCM tokens / Artifactory creds / Slack webhooks are stored as **Jenkins or GitHub Actions secrets**, never in the repo.  

#### Step 2 – Merge to `main` and build pipeline runs

1. On merge, CI kicks off `orders-api-build` pipeline.  
2. Pipeline steps:
   - Build Docker image.  
   - Tag image: `artifactory.mycorp.com/my-docker-virtual/orders-api:build-123`.  
   - `docker login` using CI credentials → push to Artifactory Docker repo.[web:245][web:247]  

Artifacts:

- Docker image lives in Artifactory (private registry).  
- Build metadata (Git commit, branch, build number) attached in Artifactory for traceability.[web:243][web:248]  

#### Step 3 – Update GitOps repo (Argo CD)

1. Jenkins updates Helm values in GitOps repo:
   - `values-prod.yaml`:
     ```yaml
     image:
       repository: artifactory.mycorp.com/my-docker-virtual/orders-api
       tag: "build-123"
     ```
2. Commit is signed/verified and pushed to Git (GitOps manifest repo).  
3. Jenkins optionally calls Argo CD API:
   - `argocd app sync orders-api-prod`.  

Secrets here:

- Only **secret references** are in values (Secret names, not actual keys).  
- Real secrets exist as:
  - Kubernetes Secrets in cluster, populated from AWS Secrets Manager / Ansible Vault / Jenkins.  
  - Or via Argo CD’s secret integration (e.g., Vault plugin).[web:228][web:235][web:238]  

#### Step 4 – Argo CD syncs to Kubernetes

1. Argo CD sees Git change → syncs manifests to EKS and/or on‑prem cluster.  
2. K8s Deployment updated with new image tag and same Secret references.  
3. K8s pulls Docker image from Artifactory using `imagePullSecret` configured with Artifactory robot user.[web:245]  

At runtime:

- Container starts with env vars from Kubernetes Secrets (`DB_USER`, `DB_PASS`, API keys).  
- Secrets are isolated per namespace and environment (dev/stage/prod).  

#### Step 5 – Monitoring and email alerting

1. Prometheus scrapes:
   - K8s Pods and nodes for `up` metrics.  
   - Application metrics (HTTP status codes, latency).  
2. Alert rules:
   - `up == 0` → `InstanceDown` or `ServiceDown`.  
   - High 5xx rate → `HighErrorRate`.  
3. Alertmanager routes `severity=critical` alerts to:
   - Email receiver → `devops-oncall@company.com`.  
4. In AWS, CloudWatch may also have alarms on:
   - EC2 instance status, ELB 5xx, or custom Lambda health.  
   - These publish to SNS → email to the same on‑call list.[web:257][web:262][web:265]  

**Result**

- If the new version crashes Pods:
  - `up == 0` or readiness fails → Prometheus alert → Alertmanager → email.  
- If the whole node dies:
  - Node exporter stops responding → node‑level alert.  
- If AWS infra is affected:
  - CloudWatch → SNS → email.

## 11. Scenario‑based Q&A (Practice)

### Q1. “How do you ensure secrets are safe from code commit to runtime in Kubernetes?”

**Answer outline**

1. **Code & CI**  
   - No secrets in code. Everything sensitive is in Jenkins / GitHub Actions credentials or Ansible Vault / AWS Secrets Manager.  
2. **Terraform / Ansible**  
   - Terraform variables marked `sensitive`; values injected as `TF_VAR_` from Jenkins.  
   - Ansible Vault encrypts sensitive vars; vault password stored in Tower/Jenkins credentials.[web:232][web:237]  
3. **Kubernetes**  
   - Kubernetes Secrets used per environment and namespace; access controlled via RBAC.  
   - Argo CD manifests only reference Secret names, not values.[web:226][web:229][web:238]  

### Q2. “Where do Docker images live in your ecosystem and how are they used?”

**Answer outline**

1. Docker images built in CI (Jenkins / GitHub Actions).  
2. Pushed to JFrog Artifactory Docker registry with proper tags and metadata.[web:242][web:247]  
3. Kubernetes (via Argo CD) pulls images from Artifactory using `imagePullSecrets`.  
4. No direct pulls from Docker Hub in production; Artifactory acts as the single registry and cache.[web:245][web:249]  

### Q3. “What happens when a production node or application goes down?”

**Answer outline**

1. Prometheus detects `up == 0` or application health failures.  
2. Alertmanager groups and routes alerts (critical) to email receiver (on‑call list).[web:257][web:261]  
3. For AWS resources, CloudWatch Alarms on status checks or ALB metrics publish to SNS and send email notifications.[web:262][web:266]  
4. On‑call engineer investigates with logs (CloudWatch / Grafana / Kibana) and metrics dashboards.

## 12. Scenario Set – Secrets, Artifacts, Deployment, Alerts

### Scenario 1 – Rotating a production DB password end‑to‑end

**Question**  
“Your production PostgreSQL password must be rotated. Explain step by step how you do this across Ansible/Terraform, Kubernetes, and Argo CD without downtime.”

**Answer (story)**

1. **Plan rotation (no changes yet)**  
   - Confirm which services use the DB: for example, `orders-api`, `billing-api`.  
   - Identify where the current password lives:
     - Ansible Vault vars (for DB bootstrap / admin tasks).  
     - Terraform variable or secret manager.  
     - Kubernetes Secret `orders-api-db-secret` in `prod` namespace.[web:226][web:229][web:232]  

2. **Generate new password in secure place**  
   - Generate strong password locally or via secret manager (AWS Secrets Manager, Vault).  
   - Update Ansible Vault file (e.g., `group_vars/prod/vault.yml`) with the new password:
     ```bash
     ansible-vault edit group_vars/prod/vault.yml
     ```
   - This keeps the new value **encrypted in Git**, not in plain text.[web:232][web:237]  

3. **Update DB server using Ansible**  
   - Run Ansible playbook that:
     - Logs into DB using old password.  
     - Changes the DB user password to the new value.  
   - Playbook reads new password from Vault‑encrypted vars.  
   - Vault password is injected via Ansible Tower or Jenkins credentials, not typed manually.  

4. **Update secret source for apps (Terraform / secret manager)**  
   - If DB password is mirrored in a cloud secret store (e.g., AWS Secrets Manager), update that secret through Terraform or CI:
     - Terraform: `var.db_password` updated via pipeline variable; run `terraform apply`.  
     - Or a small Python/boto3 script updates the secret in AWS Secrets Manager.[web:196]  

5. **Update Kubernetes Secret (no downtime yet)**  
   - Regenerate Kubernetes Secret manifest (or use External Secrets operator):
     ```bash
     kubectl create secret generic orders-api-db-secret \
       --from-literal=username=orders_user \
       --from-literal=password='<new-password>' \
       -n prod \
       --dry-run=client -o yaml | kubectl apply -f -
     ```
   - This updates the Secret in place; existing Pods still use old connections until restarted.  

6. **Rolling restart via Argo CD (zero downtime)**  
   - Update GitOps repo if Secret is generated there, or simply let Argo CD see that the Secret changed.  
   - Trigger a rolling restart of `orders-api` Deployment (e.g., patch annotation or new image tag).  
   - Argo CD ensures the Deployment rolls gradually:
     - New Pods come up using new Secret (new password).  
     - Only when new Pods are `Ready` are old Pods terminated.  

7. **Verify and clean up**  
   - Check application logs and health endpoints to confirm successful DB connections.  
   - Prometheus/Grafana dashboards show no spikes in errors or latency.  
   - Optionally remove the old password from any remaining locations (if stored temporarily).  

**Key phrases you can say**

> “We treat DB rotation as a multi‑step process: update the DB via Ansible using Vault‑encrypted vars, update the source of truth for secrets (Terraform/Secrets Manager), then update Kubernetes Secrets and let Argo CD roll workloads so they pick up the new password without downtime.”

### Scenario 2 – New microservice onboarded with Artifactory, Jenkins, Argo CD, secrets, and email alerts

**Question**  
“A new service `payments-api` needs to be onboarded to your platform. How do you integrate it into CI/CD, Artifactory, Kubernetes secrets, and alerting?”

**Answer**

1. **CI & Artifactory setup**

   - Add steps:

     - Tag as `artifactory.mycorp.com/my-docker-virtual/payments-api:${BUILD_NUMBER}`.

2. **GitOps repo and Argo CD app**  
   - Add Helm chart or Kustomize folder for `payments-api` in GitOps repo:
     ```yaml
     image:
       repository: artifactory.mycorp.com/my-docker-virtual/payments-api
       tag: "build-1"
     ```
   - Create Argo CD `Application` pointing to this path and the target cluster/namespace.[web:236][web:239]  

3. **Secrets for `payments-api`**  
   - Identify secrets:
     - Payment gateway API key.  
     - DB credentials.  
   - Store them in secure source:
     - Ansible Vault vars, or  
     - Cloud secret manager (AWS Secrets Manager / Azure Key Vault).  
   - Create Kubernetes Secrets in `payments` namespace (via Terraform/Ansible/CI):
     ```bash
     kubectl create secret generic payments-api-secret \

     ```[web:226][web:229][web:235]

   - Alertmanager routes `severity=critical` alerts to email (on‑call group).  

**Key phrase**

> “Onboarding a new microservice is mostly wiring: CI builds/pushes to Artifactory, Argo CD syncs manifests from Git, secrets are created in Kubernetes from Vault/secret manager, and Prometheus/Alertmanager plus email make sure we know if the service goes down or misbehaves.”

**Question**

**Answer**

1. **Detection**  
   - Jenkins showed the node as offline; builds targeting that label queued or failed.

   - If capacity issue: scale up auto‑scaling group or add more static agents.  
   - Update runbooks/SOPs with root cause and fix steps.  

**Key phrase**

> “Jenkins itself surfaced the agent offline, but we relied on Prometheus + Alertmanager email alerts on the underlying node metrics to be proactively notified when a Jenkins build node was down, so we could restore capacity before it impacted many pipelines.”

### Scenario 4 – GitOps drift and secrets

**Question**  
“What happens if someone changes a Deployment or Secret manually with kubectl in production, and how do you handle that with Argo CD and secrets?”

**Answer**

1. **Manual change occurs**  
   - Someone runs `kubectl edit deployment orders-api -n prod` and changes an env var or image tag directly.  

2. **Argo CD detects drift**  
   - Argo CD compares live state vs Git state.  
   - Application status shows “OutOfSync” for `orders-api`.[web:238][web:239]  

3. **Decision**  
   - If change is unintended:
     - Click “Sync” or run `argocd app sync` to revert cluster back to Git‑desired state.  
   - If change is desired:
     - Apply same change in Git (values.yaml/manifest) and let Argo CD sync properly.  

4. **Secrets consideration**  
   - If secret values are managed externally (Vault/Secrets Manager), manual changes to K8s Secrets are overwritten next sync.  
   - Team process: treat Git as the source of truth for config references and treat Vault/secret manager as source of truth for actual secrets.  

**Key phrase**

> “If anyone changed Deployments or Secrets directly with kubectl, Argo CD showed drift and we either reverted to Git or updated Git to match the approved config. For secrets, we treated Vault/Secrets Manager + Git references as the source of truth rather than ad‑hoc manual changes.”

## 13. Scenario Set – Security, Hybrid, and Incident Handling

### Scenario 5 – Detecting a leaked secret and responding safely

**Question**  
“Imagine a developer accidentally commits a plaintext password or API key to a Git repo. What do you do, step by step, in your environment?”

**Answer**

1. **Detection**  
   - Secret detection tool (e.g., GitHub secret scanning, pre‑commit hook, or manual code review) flags a secret in a commit.  
   - Ticket created in Jira/ServiceNow to track the incident.  

2. **Immediate containment**  
   - Treat the secret as **compromised**.  
   - Revoke or rotate the secret in its **source of truth**:
     - For DB: change password using Ansible/SQL.  
     - For API key: revoke key and generate a new one in provider portal.  

3. **Update secret stores and code**  
   - Update Ansible Vault / Secrets Manager with new value.  
   - Replace plaintext secret in code with a **reference** to the vault/secret:
     - Environment variable name.  
     - Kubernetes Secret key reference.  

4. **Invalidate Git history copy**  
   - Remove or redact leaked secret from repo history where possible (or at least from active branches).  
   - Add or update secret scanning checks in CI to prevent similar incidents.  

5. **Redeploy dependent services**  
   - Any service using the old secret is redeployed:
     - Kubernetes Secrets updated.  
     - Argo CD sync triggers rolling updates.  
   - Verify logs/metrics to confirm services use new credential.  

6. **Post‑incident follow‑up**  
   - Document root cause and remediation in RCA.  
   - Train dev team on secret handling (use vaults, not code).  

**Key phrase**

> “We treat any leaked secret as compromised: rotate it at the source, update Vault/Secrets Manager and Kubernetes Secrets, redeploy via Argo CD, and then patch our process (e.g., CI secret scanning) so the issue cannot reoccur.”

### Scenario 6 – Hybrid app: on‑prem app calling AWS service with secure credentials

**Question**  
“How does an on‑prem application in your environment securely call AWS services (e.g., S3) without hardcoding keys?”

**Answer**

1. **Central secret management**  
   - Create IAM user or role with least privileges (e.g., S3 read on specific bucket).  
   - Store access key and secret key in **Ansible Vault** or a corporate secret manager.  

2. **Configuration to on‑prem server via Ansible**  
   - Ansible playbook:
     - Decrypts credentials from Vault.  
     - Writes them into a secure config file on the server (e.g., root‑only permissions), or  
     - Injects them into a systemd service environment file.  

3. **Application configuration**  
   - Application reads credentials from:
     - Environment variables, or  
     - Config file restricted to service user.  
   - Application uses SDK (boto3/official SDK) with these credentials to call AWS.  

4. **Rotation process**  
   - When rotating keys:
     - Update in AWS IAM.  
     - Update in Ansible Vault.  
     - Run Ansible to push new credentials to on‑prem hosts.  

5. **Monitoring & alerts**  
   - CloudWatch + SNS alarms on unusual API usage patterns or access denied spikes.  
   - Email alerts to security/DevOps if suspicious activity is detected.  

**Key phrase**

> “For hybrid scenarios, we stored AWS credentials securely in Ansible Vault and pushed them to on‑prem services with restricted permissions. Apps consumed them from environment/config files, and we had a process to rotate and monitor those credentials through IAM and CloudWatch.”

### Scenario 7 – Multi‑cluster GitOps (dev, stage, prod) and secret segregation

**Question**  
“You have multiple Kubernetes clusters: dev, stage, prod (some on‑prem, some in AWS/Azure). How do you manage secrets and deployments across them using Argo CD and GitOps?”

**Answer**

1. **Per‑environment Git structure**  
   - Separate directories or repos:
     - `environments/dev/`, `environments/stage/`, `environments/prod/`.  
   - Each has its own values/overlays:
     - Resource limits, replica counts, and **Secret names** may differ.  

2. **Per‑cluster Argo CD Apps**  
   - One Argo CD `Application` per environment:
     - `orders-api-dev` → dev cluster.  
     - `orders-api-prod` → prod cluster.  
   - All driven from Git, each app points to a relevant path and cluster context.[web:236][web:239]  

3. **Secret management**  
   - Dev secrets:
     - Often lower sensitivity, maybe stored directly in Kubernetes Secrets (but still not plain in Git).  
   - Prod secrets:
     - Must come from more secure source (Vault/AWS Secrets Manager), synced into clusters via External Secrets or CI.  
   - No secret values in Git; only references like Secret names and keys.  

4. **RBAC and access**  
   - Dev clusters: more people allowed; production clusters: limited admins and Argo CD service accounts.  
   - Separate ServiceAccounts and `imagePullSecrets` for each cluster, pointing to appropriate Artifactory repos.  

5. **Promotion**  
   - Dev → Stage → Prod promotion is done by:
     - Updating tags or values in respective environment directories.  
   - No direct kubectl in prod; Argo CD syncs from Git for each cluster.  

**Key phrase**

> “We used Argo CD to manage separate Applications per environment, with environment‑specific values and secret references. Secrets themselves came from secure stores and were never shared between dev/stage/prod, which kept production credentials isolated even though manifests lived in common Git repos.”

### Scenario 8 – Handling a failed deployment with quick rollback

**Question**  
“If a production deployment via Argo CD introduces errors and user impact, how do you roll back safely?”

**Answer**

1. **Detection**  
   - Prometheus/Grafana show:
     - Increased 5xx errors or latency.  
   - Alertmanager sends critical emails to on‑call.  
   - User reports / dashboards confirm impact.  

2. **Identify change**  
   - Check Argo CD Application history:
     - See recent sync (which Git revision or image tag was deployed).  
   - Check Git history for that app:
     - Config changes, image tag updates.  

3. **Rollback decision**  
   - Decide whether to:
     - Roll back to previous Git commit (Git history), or  
     - Roll back image tag (e.g., from `build-123` to `build-122`).  

4. **Execution**  
   - Edit values in Git (e.g., `image.tag: "build-122"`).  
   - Commit and push.  
   - Argo CD sees change and syncs, performing a rolling update back to older version.  

5. **Secrets consideration**  
   - Secret references remain unchanged; secrets themselves were not altered in this deployment.  
   - If the issue is secret‑related (e.g., wrong credential), fix the secret in secret manager and resync instead of rolling back code.  

6. **Verification**  
   - Monitor metrics again: error rates, latency return to normal.  
   - Confirm via health checks and user feedback.  

7. **Post‑incident**  
   - Open incident ticket, document root cause (bad config vs bad code vs infra).  
   - Add tests or checks to catch similar issues earlier (staging, smoke tests).  

**Key phrase**

> “Argo CD’s Git history and application history make rollbacks straightforward: we revert the Git change (usually image tag or config), let Argo CD apply the rollback, and use Prometheus/Grafana to confirm stability. Secrets generally remain stable across rollbacks, unless the incident is specifically secret‑related.”
